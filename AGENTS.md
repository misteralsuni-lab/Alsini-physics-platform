# Agent Guide — Alsini Physics Platform

## GitHub Issues & Backlog Workflow

GitHub Issues are the source of truth for queued work. Run `gh` commands from the repository root.

| Label | Meaning |
|---|---|
| `hitl` | Human-in-the-loop supervised task |
| `afk` | Autonomous loop task (requires passing tests) |
| `blocked` | Blocked by another issue |
| `qa` | Ready for QA verification |

### Finding work

- Human-in-the-loop queue: `gh issue list --state open --label hitl`
- Autonomous queue: `gh issue list --state open --label afk`
- Ignore issues labeled `blocked`, and issues whose body contains an unresolved
  `Blocked by #<id>` dependency. Check the referenced issue's state before starting.

### Loading issue context

At the start of every session, run `gh issue view <number> --comments` to read the
full specification, acceptance criteria, and prior discussion before changing code.
(On `gh` CLI versions affected by the Projects (classic) GraphQL deprecation, pass
`--json number,state,title,body,comments`.)

### Progress and handoff trace

Post implementation notes, test results, blockers, and QA findings directly on the issue:

```bash
gh issue comment <number> --body "..."
```

Treat the issue thread as the audit trail. A fresh session must be able to reconstruct
spec → implementation → verification from the issue alone.

### Closing issues

- Reference the issue in commits/PRs with `Closes #<number>` when the work is complete.
- Use `Refs #<number>` for partial work that should not close the issue.
- When implementation is complete but verification is pending, add the `qa` label
  instead of closing.
- Only close after the acceptance criteria are met and the verification path is
  recorded on the issue.

### Repo mirror for specs

Whenever a parent PRD or multi-slice spec is created, save a Markdown copy under
`docs/prd/` (for example `docs/prd/<slug>.md`) so repository-level reviewers can read
it alongside the codebase. Link the issue and the mirrored file to each other.

## Git & GitHub Issue Workflow (Mandatory)

Every repository change made by an AI agent MUST follow this end-to-end workflow —
no exceptions:

1. **Create a tracking issue first.** Before any file is staged, edited or committed,
   open a GitHub issue with `gh issue create` (run `gh` commands from the repository
   root). No issue → no change.
2. **Reference the issue in the commit message.** The commit that lands the change
   MUST include `Closes #<issue_number>` in its message.
3. **Push to the active branch.** The single active production branch is `main`
   (the repository default branch). Push the commit to `origin main`.
4. **Verify closure.** After pushing to `origin main`, run
   `gh issue view <issue_number> --json number,state,title,url` to confirm
   the issue closed automatically via `Closes #<issue_number>`. If GitHub
   has not closed it (or when pushing to a non-default branch), close it
   explicitly with `gh issue close <issue_number>` and re-verify with
   `gh issue view <issue_number> --json number,state,title,url`.
   Same-session verification is part of the change — an unverified workflow is an
   incomplete change.

## Production Branch & Deployment Alignment

`main` is the single production branch for this repository:

- **Backend (Render):** Deployed from `main` via root `render.yaml`
  (`name: alsini-physics-backend`, `rootDir: backend`, Python `3.11.15` from
  `.python-version`, `buildCommand: pip install -r requirements.txt`,
  `startCommand: uvicorn main:app --host 0.0.0.0 --port $PORT`,
  `healthCheckPath: /health`). Never commit secrets; keep secret env vars
  marked `sync: false` in `render.yaml` and managed in the Render Dashboard.
- **Frontend (Vercel):** Deployed from `main` with Root Directory `frontend`
  (Vite build, SPA rewrite in `frontend/vercel.json`).
- **Legacy history:** Pre-promotion `main` (`6090fa1`) is preserved on `origin`
  under tag `archive/legacy-main-pre-promotion`.

## `.vercel` Artifacts

Local Vercel CLI output (`.vercel/` directories, e.g. at the repo root and in
`frontend/`) is generated by `vercel link`/`vercel deploy` and MUST stay
untracked. It is ignored via `.gitignore`; never commit `project.json`,
`README.txt`, or nested `.gitignore` files from Vercel link directories. If a
directory was committed before, remove it from the index with
`git rm -r --cached <dir>/.vercel` and commit the removal under its own tracking
issue.
