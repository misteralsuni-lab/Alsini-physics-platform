## 1. Executive Decision

# **NO-GO — Session 4A.1 is not approved for Session 4B entry yet**

The implementation is materially improved and the main LearningContext path is structurally sound, but the verification identified unresolved correctness and release-integrity risks:

1. Focused-asset citation labels are still generated by the client and are not canonicalized by the backend.
2. Graph formula grounding is not deterministically related to the selected graph.
3. Chapter/resource state can cross-contaminate during route changes or stale asynchronous responses.
4. Resource selection still defaults to the first specification point/resource rather than an authoritative worksheet mapping.
5. Live authenticated, Supabase-backed, RAG, storage, and browser verification has not completed.

The Lesson, Practical Investigation, Quiz Engine, Progress Tracking, and Teacher Analytics surfaces are intentionally future work in the project roadmap. Their absence is not treated as a failure of the current Worksheet slice, but their integration contracts must be finalized during Session 4B before those surfaces are released.

Approval can be granted after the remaining worksheet-slice blockers are fixed and a live authenticated regression run passes.

## 3. Architecture Review

### 3.1 Hierarchy and pedagogical architecture

The Unit → Chapter → Worksheet hierarchy remains intact. No Lesson, Practical, Quiz, Progress, or Teacher Analytics redesign was introduced.

The current implementation correctly treats `LearningContext` as a generic carrier intended to support future surfaces:

- `resource_id`
- `chapter_id`
- `lesson_id`
- `block_id`
- `worksheet_id`
- focused chunk/asset/question/page fields

This is a suitable additive integration boundary for Session 4B. However, only resource and focus fields currently influence tutor retrieval and prompting. Lesson/block fields are schema-level compatibility only and remain deferred behavior.

### 3.2 Frontend architecture

The current frontend flow is:

```text
Chapter route
  → InteractiveTutor
  → resource/specification lookup
  → HybridDocumentViewer
  → focus state
  → LearningContext
  → authenticated FastAPI request
```

The separation between viewer focus, tutor state, search, and API transport is appropriate for the current slice. `authenticatedFetch` centralizes bearer-token propagation without changing the component hierarchy.

Remaining frontend concerns:

- resource resolution is indirect and defaults to the first specification point/resource;
- route-scoped state is not fully reset when `chapterId` changes;
- stale resource/viewer requests have no cancellation or generation guard;
- document-mode asset focus uses a clickable container rather than a keyboard-native button;
- the Lesson tab remains a placeholder by design and is deferred to Session 4B.

### 3.3 Backend architecture

FastAPI is now the active backend contract for the current frontend. `backend/package.json` starts Uvicorn rather than the legacy Express server.

The FastAPI surface now has:

- Supabase bearer-token validation;
- explicit CORS origins rather than wildcard CORS;
- authenticated `/api/tutor`, search, asset, question, and grade routes;
- dynamic resource-scoped tutor retrieval;
- focused-asset/resource relationship verification;
- additive asset provenance fields in `TutorSource`.

The legacy Express server remains in the repository. It must not be deployed as the active API unless its authentication and contract are separately hardened.

### 3.4 Authentication and authorization

Authentication is now enforced at the FastAPI boundary. The server validates the Supabase token through Supabase Auth and verifies that a user identity is returned.

Grading now rejects a client-supplied `student_id` that does not match the authenticated user.

Remaining authorization debt:

- the authenticated user is not yet checked against resource ownership/enrollment;
- curriculum tables and storage are intentionally public in the current migrations;
- service-role Supabase access bypasses downstream RLS for FastAPI data calls;
- private worksheets, teacher-only resources, or tenant-specific content require a separate authorization policy before introduction.

This is acceptable only while the documented curriculum content remains public and grading identity is treated as the protected user boundary.

## 4. API Contract Review

### 4.1 Tutor contract

The preferred contract is now:

```json
{
  "student_prompt": "...",
  "history": [],
  "resource_id": "...",
  "learning_context": {
    "resource_id": "...",
    "chapter_id": "...",
    "focused_chunk": "...",
    "focused_asset": "...",
    "focused_asset_label": "...",
    "focused_asset_type": "...",
    "focused_question": "...",
    "page": 2
  }
}
```

The legacy top-level `resource_id` remains accepted for backward compatibility. Conflicting top-level and nested resource IDs are rejected.

### 4.2 Search contract

Search requests are authenticated and resource-scoped when a worksheet resource is selected. The selected chunk type is now applied to the relational path and enforced on returned vector results.

Remaining quality debt: vector results are filtered after the RPC’s limited top-N response. A future migration can add chunk type directly to the RPC without changing the frontend contract.

### 4.3 Asset contract

The backend verifies that `focused_asset` belongs to the selected `resource_id` before grounding. This closes the highest-risk asset/citation mismatch path.

Remaining defect: the compact asset label is still computed from frontend ordering and reused in the backend prompt/source. The backend must derive one canonical label from verified asset metadata or a persisted ordinal.

### 4.4 Grade contract

The existing request shape remains compatible, but the authenticated identity is now authoritative for `student_id`.

The broader Quiz contract remains incomplete: question identity, mark scheme identity, resource-scoped question retrieval, retry semantics, authoritative grading data, and attempt persistence are not yet defined. Those are deferred because Quiz is explicitly later in the project vertical sequence.

## 8. Citation System Review

### Confirmed behavior

- Tutor sources contain resource and chunk traceability fields.
- Focused synthetic asset sources include asset ID and URL fields.
- Student mode exposes compact citation labels and human-readable resource/page/specification data.
- Developer mode exposes expanded provenance.

### Release blocker

The focused asset label is not yet server-canonical.

**Root cause:** the frontend derives labels from array index and the backend accepts the submitted label after verifying only the asset/resource relationship.

**Impact:** a reordered asset list or crafted request can produce a label that does not identify the verified asset.

**Recommended fix:** derive the label from verified `storage_path`/asset metadata or persist a canonical ordinal. Use the same value in:

- the tutor preamble;
- the synthetic `TutorSource`;
- the frontend focus chip;
- the developer provenance view.

**Files:**

- `backend/main.py`
- `frontend/src/components/HybridDocumentViewer.jsx`
- `frontend/src/components/InteractiveTutor.jsx`
- `migrations/mig_5_resource_assets.sql` if persistence is selected

## 9. Graph Synchronization and RAG Review

### Confirmed behavior

- Focused asset identity reaches the tutor endpoint.
- Asset/resource mismatches are rejected.
- On-page chunks are retrieved using resource and page metadata.
- Linked question grounding is supported when `linked_question_id` is populated.
- General RAG retrieval is dynamically scoped to the selected resource.

### Release blocker

Graph formula grounding is not deterministic.

**Root cause:** graph focus retrieves a limited number of formula chunks for the entire resource without an explicit relationship to the focused graph. The query currently requests `chunk_type=eq.formula`, while the migration and embedding pipeline define the stored type as `formula`, so the current path may also return no formula context at all.

**Impact:** an unrelated equation may be presented as the governing formula, or the intended formula may be silently omitted, creating a pedagogical and citation error.

**Recommended fix:** retrieve formulas only through an explicit asset metadata/formula-chunk relationship. If no relationship exists, omit the formula rather than guessing.

**Files:**

- `backend/main.py`
- `backend/pipeline/embedding_pipeline.py`
- `migrations/mig_5_resource_assets.sql`
- `migrations/mig_6_resource_chunks.sql`

Image-pixel multimodality is not currently implemented. The safe interim contract is text/caption/OCR grounding only; the tutor must not claim to inspect graph axes or values absent from verified text.

## 10. Prompt Engineering and Hallucination Prevention

### Confirmed safeguards

- Tutor persona is Socratic and avoids immediately revealing final answers.
- Retrieved context is explicitly cited by source number.
- Page numbers are constrained to retrieved metadata.
- No-context requests now receive an explicit ungrounded-context instruction.
- Asset focus instructs the tutor not to ask the student to describe an already selected asset.

### Remaining risk

The no-context safeguard is prompt-only. The LLM can still generate unsupported content when retrieval fails, and a synthetic asset caption alone is not sufficient evidence for detailed visual claims.

### Recommended deferred hardening

Add an explicit `grounding_status` response field and a UI disclosure, or fail closed for high-stakes curriculum questions with no verified context. This should be addressed before Progress Tracking or authoritative Teacher Analytics rely on tutor correctness.

## 11. Pedagogical Review

The implementation remains aligned with the project philosophy:

- the student navigates Unit → Chapter → Worksheet;
- specification points remain curriculum metadata rather than primary student navigation;
- the tutor guides through questioning rather than immediately answering;
- worksheet focus provides context without forcing the student to restate visible content;
- citations remain compact in student mode and detailed in developer mode.

The main pedagogical risk is incorrect graph/formula association. A tutor that confidently supplies an unrelated equation is worse than one that states that no verified governing formula is available. Formula grounding should therefore fail closed until the relationship is authoritative.

## 12. Scalability Review

### Positive findings

- RAG retrieval is bounded to a small top-N result set.
- Asset grounding deduplicates chunk IDs.
- Resource-scoped retrieval limits cross-worksheet contamination.
- The generic LearningContext can be extended to future surfaces without changing `/api/tutor`.
- Authenticated transport is centralized in the frontend.

### Scalability risks

- Supabase Auth is called for each API request; this is correct for the current verification boundary but may require token/JWKS caching at higher volume.
- Page grounding must remain server-filtered and deterministically ordered.
- Post-RPC chunk-type filtering can return fewer results than requested.
- Service-role access and public RLS policies are unsuitable for future private/tenant-scoped content.
- Resource selection cannot remain “first resource” as multiple worksheets, lessons, and practicals are introduced.
